# 可见光 4K 预览延迟优化（2026-09-20）

## 1. 现象

选择「主码流 4K (101)」时，画面延迟约 20 秒以上，且延迟随时间持续增大。

## 2. 根因分析

| # | 根因 | 说明 |
|---|------|------|
| 1 | **appsink 队列无限制** | 管线中 `appsink` 未设置队列属性，GStreamer 默认 `max-buffers=200`、`drop=false`。解码/转换速度低于相机 25fps 时缓冲持续积压，积压 160 帧即约 **20 秒延迟**，且延迟不断增长。 |
| 2 | **CPU 上做 4K 格式转换** | `videoconvert` 把 4K BGRx→BGR，每帧需读写各约 24MB，是掉帧的主要来源；而 `nvvidconv` 本身已能在 GPU 内输出 BGRx。 |
| 3 | **接收端时钟 Slave** | `rtspsrc` 默认 `buffer-mode=auto`，会 Slave 到相机时钟并做漂移校正，引入额外缓冲等待。 |
| 4 | 4K 原生预览的 GPU→CPU 拷贝 | 4K BGRx 每帧 33MB 需从 GPU 拷回内存，实测采集仅约 12fps。 |

## 3. 修改内容

### 3.1 采集管线（`src/visiblecamera.cpp`）

```
rtspsrc location=... latency=0 timeout=... protocols=tcp drop-on-latency=true
        buffer-mode=0 ntp-sync=false do-retransmission=false      # 不等时钟、不重传
  ! rtph265depay ! h265parse
  ! nvv4l2decoder enable-max-performance=1 disable-dpb=true       # 低延迟, 不留多余参考帧
  ! nvvidconv ! video/x-raw,format=BGRx                          # GPU 内完成转换
  ! appsink max-buffers=1 drop=true sync=false                    # 队列深度 1, 只取最新帧
```

- 去掉 `videoconvert`：BGRx 内存布局与 `QImage::Format_RGB32` 一致，界面侧零转换直接使用（软解后备链路仍会自动转 BGRA）。
- 新增每秒一条采集/丢帧日志，便于评估效果。

### 3.2 预览分辨率策略（`src/mainwindow.cpp`）

- 主码流 4K 时默认由 `nvvidconv` 在 GPU 内缩放到 **1920x1080** 后输出预览；
- 可见光页新增复选框 **「预览 4K 原生(约12fps, 更吃资源)」**，勾选后恢复 4K 原生预览（配置项 `visible/native_preview_4k`）；
- **录像不受任何影响**：始终 `-c:v copy` 直拷所选码流，主码流录像仍是 4K；
- 新增策略说明标签，明确「解码 / 预览 / 录像」三者分辨率关系。

## 4. 实测对比（Jetson Xavier NX，主码流 4K H.265，25fps）

| 项目 | 优化前 | 优化后 |
|------|--------|--------|
| 采集帧率 | 约 16.6 fps | **25.1 fps（满帧）** |
| 采集队列积压 | 最多 200 帧（约 20 秒延迟，且持续增长） | **1 帧（近实时）** |
| CPU 4K 格式转换 | 每帧读写各 24MB | 无（GPU 内完成） |
| 画面延迟 | 20 秒以上 | 亚秒级 |

## 5. 相关配置

| 配置项 | 位置 | 说明 |
|--------|------|------|
| `visible/rtsp_url` | `config/default.ini` | 可见光码流，当前为主码流 `Channels/101`（4K） |
| `visible/native_preview_4k` | 同上（程序自动写入） | `false`(默认) = GPU 缩放 1080p 预览；`true` = 4K 原生预览 |
